### 实现：在 demo_vuer_vr.py 增加位姿模式开关

所有机器人部件位姿只经过一个出口 `matrix_from_pose(pos, rot)`，因此开关只加在这里：

```
POSE_MODE = "raw" | "identity" | "converted"     # 默认 raw
--raw-pose        透传 MuJoCo 原始位姿（位置+姿态都不换算）
--identity-pose   屏蔽旋转，仅保留位置（位置按 Y-up 换算）
--converted       恢复正常 Z-up -> Y-up 换算
```

- `raw`：`R = rot`（原样），`t = pos`（原样）。整机会以 Z-up 姿态出现在 Y-up
  场景里（视觉上整体倒下约 90°），但部件间相对关系与 MuJoCo 完全一致。
- `identity`：`R = I`，`t = (x, z, -y)`。只验证"位置摆位"。
- 只影响机器人；方块与手柄走各自的 three.js 坐标，不受影响。

新增 `print_pose_diagnostic()`，在模块加载时（不依赖客户端连接）打印：
- 当前 POSE_MODE 说明
- 30 个部件的原始 `geom_xpos` 表
- 换轴不变量检查：raw 与 converted 的部件间距必须一致（已实测一致 ✓）

### 实测验证（客户端实收矩阵 vs 期望值逐项比对）

## 任务：converted 模式下网页端仍显示部件散开

用户提供 converted 模式截图，机器人呈人形站立但各部件彼此散开（类似"骷髅"）。

### 根因分析
- 反编译 vuer 0.1.6 客户端 `StlView` 组件：它支持 `matrix` 属性，并按列主序
  `fromArray` 读取，与我们的构造方式一致；`Stl` 组件本身没有居中/缩放等额外处理。
- 关键发现：**vuer 加载的是原始 STL 文件顶点，而 MuJoCo 内部存储的 `mesh_vert`
  与原始 STL 顶点之间存在一个 mesh 对齐变换**。
  对比 `torso_link`：
  - raw STL 顶点中心：`(+0.0050, +0.0005, +0.0471)`（Z-up）
  - MuJoCo `mesh_vert` 中心：`(+0.0018, +0.0001, +0.0078)`（Z-up）
  - 差异 ≈ `-mesh_pos` + 微小 `mesh_quat` 旋转。
- 这个差异导致直接用 `geom_xpos/xmat` + raw STL 渲染时，每个部件会围绕自身
  原始中心而非 MuJoCo 定义的 mesh 原点定位，从而整体散开。

### 修复方案
在 `demo_vuer_vr.py` 中：
1. 新增 `quat_to_matrix()`、`mesh_offset_matrix()`：用 `model.mesh_quat/mesh_pos`
   计算 raw STL -> MuJoCo `mesh_vert` 的 4x4 列主序变换。
2. 修改 `mesh_group()` 的渲染结构：
   ```
   Group(geom world matrix)
     Group(mesh offset matrix)
       Stl(raw STL)
   ```
   这样 vuer 里的 raw STL 先被变换到 MuJoCo 的 mesh 局部坐标，再套用 geom 世界位姿，
   结果与 MuJoCo 原生渲染一致。
3. 已用三个典型部件验证 `M_offset * raw ≈ mesh_vert`（误差 < 5e-4）。

### 处理
- 清理了所有残留 demo 进程，重新启动修复后的服务（pid=43644，端口 8012）。

## 任务：用户反馈"沿 group/机器人中心点 X/Z 轴旋转 90° 就对了"

用户提供截图显示机器人仍然散开，且指出每个部件像是绕自身中心沿 X 或 Z 轴旋转 90° 后就能对齐。

### 根因分析
- 重新推导坐标系变换链：vuer 的 `Stl` 组件把原始 STL 顶点**直接当作 three.js Y-up 数值**渲染，而这些数值在 MuJoCo 语义下是 Z-up 坐标。
- 关键发现：**MuJoCo 编译时已经把 `mesh_pos/mesh_quat` 对齐变换烘焙进原始 STL 顶点**，即 `raw_STL ≈ mesh_pos + mesh_quat * mesh_vert`。因此 vuer 端不需要再用 `mesh_quat/mesh_pos` 做 mesh-specific 偏移补偿。
- 之前的 `mesh_offset_matrix` 用 `model.mesh_quat/mesh_pos` 做相似变换或左乘 `ZUP2YUP`，会把带 90° 旋转的部件（如 `waist_y_link`、`l_ankle_y_link`）进一步拧错，表现为"散开且再转 90° 就对了"。
- 用所有 30 个 visual mesh geom 的包围盒中心做数值验证：
  - 旧方案（相似变换）：平均误差 0.121m，最大 0.499m
  - 修正方案（仅固定 `ZUP2YUP` 轴向旋转）：平均误差 0.006m，最大 0.017m（剩余误差来自 STL 与 `mesh_vert` 顶点数/密度不同导致的重心偏移）

### 修复方案
在 `demo_vuer_vr.py` 中：
1. 将 `mesh_offset_matrix()` 简化为固定坐标系修正矩阵：
   - `converted` / `identity` 模式返回 `ZUP2YUP`（绕 X 轴 -90° 旋转）
   - `raw` 模式返回单位矩阵
2. 删除基于 `model.mesh_quat/mesh_pos` 的 mesh-specific 偏移计算。
3. 更新 `mesh_group()` 注释，说明中层 Group 的作用是"Y-up 数值 -> Z-up 数值"的坐标系修正。
